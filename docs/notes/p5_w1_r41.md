## Decisions I made

1. **Where the log comes from.** `EngineSource.trace(endpoint)` times the design a second
   time with a log, on first use, and keeps that graph. Per endpoint, it then:
   - copies the base log,
   - calls `trace.collect` (which appends the slack and path entries),
   - filters with the same rule as `trace.format_trace`, read from `trace.SECTIONS`, plus
     the cone from `bundle._cone(e, inf)`.

   Nothing in `trace.py` or `timer.py` changed. The result is cached per endpoint.
2. **The replay never computes.** `model.Replay` only looks up the latest reached entry:
   - `forward()` returns `at`, `slew` and the winner candidate's `delay`;
   - `rat()` comes from a backward entry or a check entry (setup = late, hold = early);
   - `slack()` comes from a slack entry.

   The Data path total (Σ, a sum) is hidden in the Trace tab. Stub arrival labels are blank,
   because they come from `source.arrival`, not the log.
3. **Badges show AT only** (`<at> <rf>`), as the non-trace badges do. RAT is in the table
   and the inspector. I clarified this in the contract.
4. **Rows outside the data path.** These are the source / input rows and the destination
   clock rows (clock edge, latency, uncertainty, library time, required).
   - They keep the path object's values (SDC terms, not recomputed).
   - They stay blank until the replay reaches the path's first point (source section) or
     the endpoint's check entry for the path's kind and rf (destination section).
   - The final slack comes from the endpoint's slack entry.
5. **Pin slack column.** In the Trace tab it shows only the endpoint's slack entry. The log
   has slack entries only for the endpoint, so other pins are blank. The inspector's slack
   rows likewise show the endpoint's slack entry for the rf of that check's worst path.
6. **Auto-expansion.** Side inputs are expanded round by round until no `expand` stub is
   left or the drawing has 300 pins or more. That counts drawn pins (each pin is a timing
   node), and stops with `truncated` shown beside the phase label. User expansions of the
   Schematic tab are not touched.
7. **Bundle mode.** The Trace tab is drawn faint, with no click target, and `set_tab("trace")`
   / key `3` do nothing. `app.replay` is `None`.
8. **Key 3.** It now opens the Trace tab. This changes the R33 test that asserted `3` was
   unbound; R41 names key 3, so that assertion changed with it.
9. **Model test for the (phase, pin) sequence.** The expected sequence is read from the
   golden text `tests/golden/trace/ff2_default_FF2_D.txt`: its section header lines, then
   each line that does not start with a space, taking its first word as the pin (for
   `path` lines, the last point's name). It is not built from `trace.py`. The result is 78
   entries.
10. **Overlap / cut-off test.** It now also covers the Trace tab, at the first entry of
    every phase and at the last entry, for every endpoint and check, over the same grid
    (8 designs × scales 0.8 / 1.0 / 1.25 × widths 1100 / 1280 / 1520).
11. **The ring has canvas tag `ring`**, so the test can find the ringed pin.
    (In the light theme the focus colour equals the ink colour, so colour cannot identify it.)
12. **Phase label placement.** The label sits at the right end of the controls row. When
    that row is too narrow, it moves to the right end of the tab row. It is never dropped.

## README paragraph

The viewer's **Trace** tab (key `3`, engine mode only) replays the engine's own log for the
selected endpoint: the same entries `--trace` prints. Use `◀ step back`, `▶ step` and
`▶▶ run to end` to move through forward propagation, the check, backward propagation, the
slacks and the worst paths. The schematic shows the whole fan-in cone with the current
pin ringed. The table and inspector show only the numbers the replay has reached, and
the inspector lists the current step's candidates, winner first.
